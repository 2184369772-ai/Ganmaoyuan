# Ganmaoyuan 30–45 Second Demo Storyboard

Use a disposable demo profile and a fully fictional project. Do not show real project names, user paths, credentials, or customer files. Capture the running Windows application; do not use mock screens.

| Time | Real action | What the viewer should understand |
| --- | --- | --- |
| 0–6s | Open Ganmaoyuan and choose the fictional recent project. | The app is a local desktop workspace, not a hosted dashboard. |
| 6–15s | Review the project’s current state and recent recorded activity. | Context comes from persisted project facts rather than a generated status claim. |
| 15–23s | Open a fictional reference document and show its project association and summary. | Files remain traceable to their project; source files are not silently moved. |
| 23–34s | Open a real Codex task and show its persisted task/run/result state. | A task is scoped to its project and its result is separately reviewable. |
| 34–42s | If a real isolated run has completed and passed the app’s verification, show the human acceptance step; otherwise show the actual current status and end without implying success. | Completion is not claimed without result, Git evidence where applicable, and human acceptance. |
| 42–45s | Return to the project workspace. | Pick up where you left off. |

## Recording checklist

- Use only synthetic filenames and content in a disposable project and Git repository.
- Start with a clean demo profile; never seed a completed Codex result or fabricate AI output.
- Show only a real task state. Do not edit labels, timestamps, Git facts, or result records for the recording.
- Keep the machine username, absolute paths, API keys, tokens, logs, and unrelated desktop windows out of frame.
- If the local Codex CLI is unavailable or the real run does not finish, omit the acceptance shot and describe the limitation rather than simulating it.
